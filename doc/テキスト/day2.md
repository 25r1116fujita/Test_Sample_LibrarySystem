# 第2日：バグ／不具合の理解と発生メカニズム

昨日は「テストの目的」を学びました。本日は、私たちが戦う相手である**「不具合（バグ）」**を正しく定義し、それがどこからやってくるのかを詳しく見ていきましょう。

## 1. 不具合の定義：3つの呼び分け

専門用語では、不具合をその状態によって3つの言葉で使い分けます。これらを区別することで、問題が「人のミス」なのか「コードの欠陥」なのかを正確に議論できるようになります。

| 用語 | 意味 | 具体例 |
| --- | --- | --- |
| **エラー (Error)** | **人間の行動**。勘違いやミス。 | 開発者が「消費税は10%」を「8%」と思い込んで設計した。 |
| **欠陥 / バグ (Defect / Bug)** | **成果物の中身**。コードや書類の不備。 | プログラム内に「* 0.08」という誤った計算式が書かれている。 |
| **故障 (Failure)** | **動かした結果**。期待通りに動かない事象。 | ユーザーが決済ボタンを押すと、誤った金額が表示される。 |

> **ポイント：** テスターが目撃するのは「故障」ですが、報告すべきは「欠陥（どこが間違っているか）」です。

---

## 2. 不具合発生のメカニズム

なぜ、優秀なエンジニアが作ってもバグは発生するのでしょうか？ 主な要因は以下の3つに分類されます。

### ① コミュニケーションの齟齬

「言った・言わない」や、解釈のズレです。

* **例：** 顧客は「スマホでも見られるように」と言ったが、開発者は「ブラウザで映ればいい」と思い、ボタンが小さすぎて押せない画面を作ってしまった。

### ② 複雑性の増大

現代のシステムは、多くの機能や外部サービス（APIなど）と連携しています。

* **例：** A機能を直したら、全く関係なさそうなB機能が壊れた（デグレード/先祖返り）。

### ③ 時間と環境の制約

* **時間：** 納期が厳しく、十分な確認ができないまま実装を進めた。
* **環境：** 開発環境では再現しないが、ユーザーの古いOSや不安定な通信環境でのみ発生する。

---

## 3. 欠陥検出の重要性（なぜ早く見つけるべきか）

バグを見つけるタイミングが遅れるほど、その修正にかかるコストやリスクは増大します。これを**「負の連鎖」**と呼びます。

| 発見フェーズ | 修正のしやすさ | 影響の大きさ |
| --- | --- | --- |
| **設計段階** | ◎ 非常に容易 | 書類を数行書き直すだけで済む。 |
| **開発段階** | ◯ 比較的容易 | 担当者がコードを書き直して再ビルドする。 |
| **テスト段階** | △ 困難 | 他の機能への影響確認（リグレッションテスト）が必要になる。 |
| **リリース後** | ✕ 絶望的 | データの復旧、謝罪、緊急メンテナンスなど莫大な損害。 |

---

## 4. テスターに求められる「欠陥検出」の視点

不具合を見つける際、以下の3つの視点を持つと、より深いバグに気づくことができます。

1. **「仕様通りか？」の視点：** * 決まったルールから外れていないかを確認する。（守りのテスト）
2. **「ユーザーならどうするか？」の視点：** * 開発者が想定していない「意地悪な操作」や「うっかり操作」を試す。（攻めのテスト）
3. **「そもそもこれで良いのか？」の視点：** * 仕様通りであっても、使いにくかったり矛盾があったりしないかを確認する。（QAの視点）

### 1. ソフトウェア品質特性（製品品質）の8分類

ISO/IEC 25010:2011で定義されている、システムそのものが持つべき8つの特性です。

| 特性 | 概要 | 主な副特性（評価観点） |
| --- | --- | --- |
| **機能適合性** | ニーズを満たす機能が提供されているか | 機能完全性、機能正確性、機能適切性 |
| **性能効率性** | リソースを効率よく使い、期待の性能が出るか | 時間効率性、資源効率性、容量満足性 |
| **互換性** | 他の製品と情報を共有・共存できるか | 共存性、相互運用性 |
| **使用性** | ユーザーにとって使いやすいか | 習得性、運用操作性、アクセシビリティ |
| **信頼性** | 故障なく安定して動き続けるか | 成熟性、可用性、障害許容性、回復性 |
| **セキュリティ** | 情報やデータを保護できるか | 機密性、真正性、責任追跡性 |
| **保守性** | 修正や改善が容易に行えるか | 解析性、修正性、試験性、再利用性 |
| **移植性** | 別の環境へ容易に移し替えられるか | 適応性、設置性、置換性 |

### 2. 利用時の品質

ユーザーが特定の状況でソフトウェアを使用した際に得られる効果に関する特性です。

* **有効性**: ユーザーの目的を正確に達成できるか。
* **効率性**: リソースを無駄にせず目的を達成できるか。
* **満足性**: ユーザーが満足（実用、信頼、快感、快適）しているか。
* **リスク回避**: 経済的、健康的、環境的なリスクを抑えられるか。
* **利用状況網羅性**: 想定された全ての状況で品質が維持されるか。

### 3. 開発現場での活用メリット

品質特性を体系的に理解することで、以下の効果が期待できます。

* **要件定義の漏れ防止**: 「使いやすさ」や「壊れにくさ」などの非機能要件を具体化しやすくなる。
* **テスト設計の最適化**: どの特性を重点的に検証すべきか優先順位を付けられる。
* **共通言語化**: 開発者、テスター、顧客の間で、品質に関する客観的な対話が可能になる。

### 結論

ソフトウェアが複雑化する現代において、品質を「目に見える形」で管理するために、これらの特性を指標として活用することが、高品質なシステム開発に不可欠であると結論付けています。

# 第2.5日：テスト計画と見積もり

これまでの研修では、仕様の理解やバグの定義を学びました。本日は、限られた時間とリソースの中で最大の品質を確保するための「戦略」である**テスト計画**について深掘りします。

## 1. テスト計画の5大要素

テスト計画は、工数の溢れや突然の仕様変更によるパニックを防ぐための「戦い方のルール」です。以下の5項目を自分の言葉で説明できるようになりましょう。

| 項目 | 内容 | テスターが意識すべきポイント |
| :--- | :--- | :--- |
| **テスト範囲 (Scope)** | 何をテストし、何をしないか | 全機能を追うと工数が足りなくなるため、対象を明確にする。 |
| **テスト手法 (Strategy)** | どうテストするか | 手動で行うか、自動化ツールを活用するか。 |
| **環境とツール** | どの端末・OSでやるか | Webアプリ特有のブラウザ依存（Safariのみ発生等）を考慮する。 |
| **リソースと計画** | 誰が、いつ、どこをやるか | メンバーのスキルや兼務状況を考慮して分担を決める。 |
| **終了基準** | 何をもって完了とするか | 「バグ0」は不可能。許容できるリスクの範囲を定義する。 |

---

## 2. リスクベースドテスト：優先順位の決定

すべてを等しくテストするのは工数的に不可能です。ビジネスへの影響度に基づき、テストの優先順位を決定します。

### 優先度判定基準（図書管理システムの例）

| 優先度 | 定義 | 対象機能の例 | 理由 |
| :--- | :--- | :--- | :--- |
| **高 (P1)** | 最優先 | **ログイン、貸出実行** | 動かないとビジネスが止まる。主要業務の根幹。 |
| **中 (P2)** | 優先 | **書籍検索、返却処理** | 頻繁に使われるが、一時的な不具合が即致命傷にはならない。 |
| **低 (P3)** | 通常 | **利用規約、デザイン修正** | 修正が容易、またはユーザー体験への影響が限定的。 |

> **テスターの視点：** 実行順序の最適化として、まず**P1（Smoke Test）**を最速で終わらせ、後のテストが継続不能になるリスクを排除します。

---

## 3. 見積もりのための基準値

* **テスト実行ペース：** 1人1日あたり平均 **40件**
* （1件10〜12分。手順確認、エビデンス撮影、記録を含む）

* **バグ発生率：** 全ケースの **約5〜10%** でバグが出ると想定
* **不具合起票・再テスト工数：** 1バグあたり **約60分**
* （不具合報告書の作成：30分 ＋ 修正後の確認テスト：30分）

* **稼働日数：** 1ヶ月を **20日** とする

* テストは全体スケジュールの30%～40%

---

## 4. 工数見積もり

見積もりには「実行」だけでなく「修正確認」の時間も含める必要があります。

### シミュレーション：10人月のプロジェクトにおけるテスト計画

#### ① 実行工数の計算

* **総テスト件数：** 1,500件
* **必要日数：** 1,500件 ÷ 40件/日 ＝ **37.5 日**
* **人月換算：** 37.5日 ÷ 20日 ≒ **約1.9 人月**（純粋なテスト実行のみ）

#### ② 再テスト・予備工数の確保（バッファ）

* **バグ対応工数：** 1,500件 × 7%（発生率） × 1時間 ≒ 105時間（**約0.7 人月**）
* **リスクバッファ：** 残りの **0.4 人月**（約8日間）
* ※合計 1.9 + 0.7 + 0.4 = **3.0 人月**

#### ③ スケジュール案（1.5人体制・2ヶ月間）

| 期間 | フェーズ | 作業内容 |
| --- | --- | --- |
| **第1〜3週** | **P1・P2実行** | 1.5人で1,000件を一気に消化。主要機能のバグを早期に出し切る。 |
| **第4〜5週** | **P3実行 ＆ 再テスト** | 残り500件の実行と、上がってきたバグの修正確認を並行。 |
| **第6週** | **予備（バッファ①）** | 予想以上にバグが多かった場合の吸収期間。 |
| **第7〜8週** | **最終予備（バッファ②）** | **後出し仕様変更**や回帰テスト、リリース判定会議の準備。 |

### シミュレーション Q&A

#### **なぜP1を最初にやるのか？**

「もし第4週目にログイン不能バグが見つかったら、そこから修正に1週間、その後のテストに2週間かかり、納期に間に合いません。リスクが高いものほど『前倒し』が鉄則です。」

#### **なぜ最後に2週間も空けるのか？**

「これが皆さんが先ほど学んだ『仕様変更への防御壁』です。何も起きなければ早く終わるだけですが、Webアプリ開発で何も起きないことは稀です。この空白があるからこそ、仕様変更が来ても『今のバッファで吸収できます』と言えるのです。」

#### **リソース（1.5人）の使い方**

「専任の1人がメインで走り、兼務の0.5人は『バグが出た時の再テスト担当』や『特定のブラウザ検証担当』としてスポットで使うと、メインの作業が中断されず効率的です。」

---

## 5. 仕様変更への対応フロー

「計画変更の合意なくして、テスト実行なし」というマインドを徹底します。仕様変更が起きた際は、以下の手順で計画を即座に修正します。

1. **変更箇所の特定**：どの機能がどう変わったか。
2. **影響範囲（回帰テスト）の特定**：修正箇所以外にどこが壊れる可能性があるか。
3. **追加工数の算出**：バッファをどれだけ消費するか、または期限を延ばすか。
4. **トレードオフの提案**：期限が延ばせないなら、優先度の低い「P3」のテストを削る提案をする。

---

## まとめ

テスターの仕事は「情報（リスク）を透明にし、チームが安心してリリースできるように支えること」です。計画を立て、優先順位を守ることで、プロジェクトのスピードと品質を両立させることができます。
